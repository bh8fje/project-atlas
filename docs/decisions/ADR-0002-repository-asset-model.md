# ADR-0002：建立 Repository Asset 抽象层

- 状态：Accepted
- 日期：2026-08-23
- Task：TASK-003

## 背景

Project Atlas 后续需要描述项目中的仓库、目录、文件、文档、源码和配置，并表达它们之间的包含、依赖与生成关系。如果发现、历史和 AI 理解能力直接使用各自的临时结构，同一个项目资产会产生不一致的身份、类型和序列化格式。

## 决策

在实现任何资产发现能力前，建立纯内存的 Repository Asset 领域契约：

- `ProjectArtifact` 表示带类型和时间信息的项目资产。
- `Repository` 表示声明的代码仓库及已知分支标签。
- `RepositorySnapshot` 表示某个时间点的仓库资产数量摘要。
- `AssetRelationship` 表示两个资产之间的有向语义关系。
- `ArtifactType` 与 `RelationshipType` 使用稳定的字符串枚举值。
- 所有模型使用不可变 dataclass，并提供基础校验及 `to_dict` / `from_dict`。

## 边界

- 路径是数据字段，不验证是否存在，也不遍历目录。
- Repository 不执行 Git 命令，不检测分支，不读取 commit。
- Snapshot 不创建快照，只描述由未来能力提供的快照数据。
- Relationship 不推断关系，只保存明确提供的关系。
- 本层不访问文件系统、网络、AI、数据库或 API。

## 后果

正面影响：

- 发现、历史和理解能力可以共享同一资产语言。
- 资产数据可在无基础设施环境下验证和测试。
- 后续持久化或 API 适配可以围绕稳定字典契约建设。

限制：

- 当前模型不保证路径对应真实项目内容。
- 当前快照只包含资产数量，不包含文件内容或差异。
- 新增资产类型、关系类型或兼容策略需要后续 ADR。
